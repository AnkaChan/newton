elasticity ALM.

The new code keeps an element’s elastic stress between iterations. Each vertex solve reads that history; one element pass updates it after every complete color sweep. This page follows those reads and writes through the actual implementation.

Current implementationCommit 246fb405CPU + CUDA tilesPlain-text equations
Start with the loop, then the state. The most important distinction is between a physical timestep, a complete VBD iteration, and a vertex color. Preparation happens per timestep. Multiplier updates happen per complete iteration. Geometry and forces are evaluated within each color.

This walkthrough describes the committed pressure / matrix formulation. The SVD formulation has not been implemented. Contact ALM belongs to the later stage of the design.

02One simulation step

SolverVBD.step() initializes the systems, interleaves rigid and particle iterations, then finalizes velocities. The particle path below runs inside that existing schedule.

CONSTRUCT ONCEAllocateArrays + tile variant PER TIMESTEPPrepareSeed if pending; compute rho PER COLORSolve verticesRead history, evaluate geometry, apply DAT PER ITERATIONUpdate dualsUse the pose after the full sweep END OF STEPFinalizeUpdate velocity; keep history 
# Reading guide: abbreviated control flow, not a literal source excerpt.
step(state_in, state_out, dt):
    initialize rigid bodies
    prepare particle ALM using incoming positions
    update collision bounds, predict positions, apply DAT

    repeat solver.iterations times:
        solve rigid-body iteration
        update particle collision detection if scheduled
        clear particle force/Hessian scratch

        for each existing particle color:
            gather contact and spring forces for this color
            evaluate membrane, hinge, and tet forces
            solve each vertex's 3x3 system
            apply existing DAT to candidate displacements

        update each elastic element's multiplier once
        copy current positions into state_out

    finalize velocities
One color is not one ALM iteration. Updating an element’s multiplier after every vertex would feed partially updated geometry into the history multiple times. The actual update is outside the color loop, immediately after the final per-color DAT call.

Per-element storage is 12 bytes per pressure-only tet, 52 bytes per full-mode tet, and 12 bytes per spring or hinge, excluding array metadata. Disabled mode allocates zero-length history arrays. Existing mesh adjacency and particle force/Hessian scratch are reused.

Persistent

lambda survives iterations and timesteps. No extra cross-step decay is applied; the per-sweep ALM recurrence still uses the factor s explained below. Initialization/reset and row retirement are the explicit history boundaries.

Recomputed

rho is recomputed once per timestep. Geometry and transmitted forces are recomputed during local evaluation. The vertex force/Hessian arrays are scratch.

04Prepare before prediction

prepare_particle_elasticity_alm() launches one pass for each present element family. It reads the incoming pose, before the predictor moves vertices. Every active row gets this step’s metric; only a pending row gets a new multiplier seed.

# Seeds represent the authored material stress at the incoming pose.
tet matrix:    Lambda_mu = mu * F
tet pressure:  lambda_p = Kp * (J - 1) - Kp * (mu / max(Kp, 1e-6))
spring:        lambda_s = K * (length - rest_length)
hinge:         lambda_b = K * (theta - rest_angle)

Kp = authored_lambda + mu
J  = det(F)
hinge K = edge_stiffness * rest_edge_length

For an ordinary rest tet, F = I. Its mu stress is mu * I, while pressure is -mu. These two contributions cancel. Zeroing both histories and immediately evaluating ALM would not generally reproduce that balance. The pressure expression avoids losing the small mu / Kp offset when forming 1 + mu / Kp at high stiffness.

Where rho comes from

invm is zero for fixed/inactive particles. w_a is a row of the inverse rest matrix; vertex 0 uses the negative sum of the other three rows. g_a = cofactor(F) * w_a is the determinant gradient for vertex a. V0 is rest volume.

tet mu rho = rho_scale / (V0 * dt^2 * sum_a(invm_a * |w_a|^2))
tet p rho  = rho_scale / (V0 * dt^2 * sum_a(invm_a * |g_a|^2))

spring rho = max(rho_scale / (dt^2 * (invm_0 + invm_1)), 9*K)
hinge rho  = rho_scale / (dt^2 * sum_a(invm_a * |grad_theta_a|^2))

The spring floor keeps its local effective stiffness at least 90% of its authored stiffness when representable. The tet pressure row has no 9*K floor, because that would bring the large pressure stiffness back into the local solve. Metric arithmetic uses float64 for the final ratio and clamps it to the representable positive float32 range.

Preparation validates a positive finite timestep. Constructor validation checks material coefficients. Zero mobility, inactive material, invalid hinges, and degenerate line elements clear the relevant row and leave it pending for recovery. Tet mu and pressure bits are handled independently.

05The same ALM row everywhere

The material coefficient K sets the converged response. The numerical metric rho determines how much stress is supplied directly by this evaluation and how much comes from the stored multiplier lambda.

s      = K / (K + rho)
k_eff  = K * rho / (K + rho)

transmitted_stress = k_eff * C + s * lambda
lambda_next       = k_eff * C + s * lambda

At convergence: lambda = K * C, so transmitted_stress = K * C.

The two expressions look identical, but their evaluation times differ: the primal reads the current local pose, while lambda_next is computed later from the pose after the entire sweep. The code implements stable ratio branches instead of forming potentially overflowing products K*rho and rho*C.

06From history to vertex forces

Tet: replace stress before assembly

evaluate_volumetric_neo_hookean_force_and_hessian_alm() forms the deformation gradient F = Ds * Dm_inv, its determinant, and the cofactor. It selects the effective coefficients before constructing the Hessian, avoiding subtraction of two large matrices.

P_mu = mu * F                                      # pressure-only mode
P_mu = k_eff_mu * F + s_mu * Lambda_mu              # full matrix mode

p_hat = k_eff_p * ((J - 1) - mu / max(Kp, 1e-6))
        + s_p * lambda_p

P       = P_mu + p_hat * cofactor(F)
force_a = -V0 * P * w_a

H_a = V0 * (mu_local * |w_a|^2 * I
            + k_eff_p * g_a * transpose(g_a))

mu_local = mu in pressure-only mode; k_eff_mu in full mode.

This is the compact expression for the force and 3×3 vertex block. The actual code constructs a 9-component stress and 9×9 material Hessian, multiplies by V0, then contracts them onto the vertex. The determinant’s second-derivative contribution cancels exactly in a single-vertex VBD block; its omission is already part of the existing formulation.

Spring: keep geometric curvature

The spring evaluator computes the transmitted axial force from the current length and stored scalar multiplier. With u the unit spring direction:

tension = k_eff * (length - rest_length) + s * lambda_s
force_0 = -tension * u
force_1 = +tension * u
H = k_eff * u * transpose(u)
    + (tension / length) * (I - u * transpose(u))

The second term is the existing geometric curvature. It can be negative in compression; this implementation does not silently replace it with an outer-product-only spring Hessian. Axial damping is added separately.

Hinge: use the existing signed angle

The authored angle-row coefficient is K_b = edge_stiffness * rest_edge_length; ALM converts it into k_eff. The elastic residual is the raw theta - rest_angle; ALM replaces the moment and stiffness feeding the existing angle gradient and outer-product Hessian. Only the damping angle increment is wrapped across ±pi.

moment  = k_eff * (theta - rest_angle) + s * lambda_b
force_a = -moment * grad_theta_a
H_a     = k_eff * grad_theta_a * transpose(grad_theta_a)
Damping is not folded into the elastic multiplier. Tet strain-rate damping, spring axial damping, and hinge angular damping are computed by their existing direct paths. Triangle membrane elasticity also stays on its existing evaluator.

07CPU and CUDA follow the same material path

The Python color loop gathers spring and contact contributions first. Then the scalar or tiled vertex kernel gathers adjacent membranes, hinges, and tets, adds inertia and the accumulated scratch contributions, and solves a 3×3 system.

Scalar kernel

solve_elasticity

One thread handles a vertex in the current color. It loops over that vertex’s existing element adjacency and calls the shared ALM evaluators.

CUDA tile kernel

make_solve_elasticity_tile

Sixteen lanes collaborate per vertex and reduce element contributions. The constructor chooses the material branches and ALM specialization once. Cloth-only work can pack two vertices into one warp.

Springs use the same element-parallel accumulation kernel before either vertex path. That kernel atomically adds contributions only to endpoints in the current color. The tiled kernel does not evaluate the spring a second time.

H_total = inertial_H + element_H + gathered_H
f_total = inertial_force + element_force + gathered_force

if the existing determinant guard accepts H_total:
    particle_displacements[vertex] += inverse(H_total) * f_total

# Back in the solver's color loop:
_penetration_free_truncation(state_in.particle_q)

The vertex kernel writes a displacement, not a new position. The subsequent truncation stage applies the candidate motion. Later colors read the resulting state_in.particle_q. particle_q_prev retains the timestep’s incoming pose for damping and final velocity.

The tiled and scalar sums can differ in rounding. The tests check numerical agreement between those paths; separate legacy tile tests check their specific bitwise equivalence guarantees.

08Update once, using the resulting pose

After the full color loop, update_particle_elasticity_alm() launches tet, spring, and hinge passes. Each element recomputes its constraint from the current positions and advances its own multiplier once. No additional coloring is introduced for these passes.

# Literal ordering at the end of _solve_particle_iteration:
    self._penetration_free_truncation(state_in.particle_q)   # inside color loop

update_particle_elasticity_alm(model, state_in.particle_q,
                              self._particle_elasticity_alm_state)
wp.copy(state_out.particle_q, state_in.particle_q)

In this stage, multipliers see positions after the existing DAT operations. They do not consume a stored untruncated attempt. Redetecting contact within an iteration does not clear structural history or apply an extra structural retention factor.

Ownership makes this parallel

Element thread e writes history slot e. The vertices are read-only during the dual pass. Neighboring elements can share vertices without racing on a multiplier array.

09Reset and CUDA capture

reset() can restore selected position/velocity fields, but ALM history invalidation happens regardless of those field flags. An element is selected if any valid endpoint belongs to a selected world. The mask’s final entry selects global entities in world -1.

solver.reset(state, world_mask=mask, flags=0)
# flags=0 leaves authored State fields alone.
# Edit state.particle_q here if needed.
solver.step(state, output, control, contacts, dt)
# The next prepare seeds selected histories from this incoming pose.

Reset clears selected multiplier/metric slots in place and marks them pending. The next preparation reinitializes them from the final incoming pose—including edits made after reset. Unselected histories are retained. For an element spanning worlds, the shared row necessarily resets when either incident world is selected.

The ALM passes perform no host readback and replace no history buffers during a step or reset. The timestep is a captured scalar argument; changing it or the launch topology requires updating/recapturing the graph. Existing contact capacity management remains a separate concern.

Repeated-interval proxy coupling is explicitly rejected. This version has no snapshot/rollback mechanism for particle elastic history, so repeating an already-solved interval would otherwise advance it twice. Rebuild the solver after topology or material changes.

10Where the matrix rotation issue comes from

At an unrotated rest pose, the full-mode multiplier is Lambda_mu = mu * I, and pressure contributes -mu * I. In the diagnostic, positions are then rotated to F = R while the old matrix multiplier is retained.

# Current implementation, immediately after that pose edit:
mu stress       = k_eff_mu * R + s_mu * mu * I
pressure stress = -mu * R

total stress    = s_mu * mu * (I - R)   # generally not zero

The current geometry rotates the direct terms; the stored world-coordinate matrix does not follow that rotation. The error therefore appears in the force itself. Pressure-only mode reads mu * F directly and has no such matrix history.

What was actually measured. A unit reference tet was abruptly rotated by 0.2 rad without resetting multipliers, velocities were set to zero, and one iteration ran at dt=1/60 s. The maximum vertex movement was about 0.110 m in full mode and 3.94e-8 m in pressure-only mode. This is a diagnostic pose-edit test, not a measurement of continuous rotational motion.

Reseeding full-mode history at the rotated pose reduces that movement to about 1.26e-7 m. It explains the source of the mismatch; it does not establish a general solution for moving scenes. The present ALM default is pressure-only.

The SVD follow-up is paused while this walkthrough is reviewed. No SVD force or history implementation is included in this snapshot.
