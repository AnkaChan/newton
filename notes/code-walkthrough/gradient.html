05 The gradient input: from physical energy to axis coordinates

Every learned query starts by measuring how the physical objective wants the current candidate to move, and that measurement is handed to the network as an input. The code lives in input_assembly.assemble_inputs(), which MixedHexSolverStep._prepare_inputs() calls once per query before the network runs. Four helpers do the work: objective_gradient() differentiates the energy with respect to corner positions, HexFusion.project_gradient() pulls that position gradient back to the per-cell axis variables through the transposed fusion solve, features.to_local() rotates the result into each cell's frame, and features.rms_normalize() scales and clips it. The previous query's gradient and the change it achieved travel with the trajectory through history.py. The whole feature is detached: it informs the network, but the training gradient never flows through it.

g       = d E_total / d X            evaluated at the candidate X, with Y and X_start fixed   [N]
g[pins] = 0
G_world = unpack(B_fᵀ K_ff⁻ᵀ g_free)   one 3 × 3 matrix per cell                                [J]
G_local = Rᵀ G_world                    same matrix in the cell's frame                          [J]
rms     = max(sqrt(mean over cells and 9 entries of G_local²), 1e-12)   one value per object
feature = clip(G_local / rms, −10, +10)  plus the scalar log(rms)

Here X holds the candidate corner positions in meters, E_total is the elastic plus inertia plus damping objective from chapter 02, K_ff and B_f are the free-corner blocks of the fusion operators from chapter 03, and R is the detached frame of each cell. The rest of this chapter follows these lines through the code.

Step 1: the position gradient of the physical objective

The first quantity is the ordinary gradient of the complete objective with respect to the shared corner positions. It is evaluated at the current candidate. The inertial prediction Y and the physical-step start X_start enter the energy as constants: they are detached before the call, so the derivative describes only how moving the candidate changes the energy. The result has one three-vector per corner and units of joules per meter, that is newtons. Its inertia part is exactly mass × (X − Y) / dt², so this vector is the full implicit-Euler residual, not the elastic force alone.

Key implementation points:

  • The function opens torch.enable_grad() and works on positions.detach().requires_grad_(True). This creates a fresh leaf tensor, so the small autograd graph built here connects to nothing else and can be evaluated even when the caller runs under torch.no_grad(), as validation does.
  • energy_total returns one energy per object, shape [B]. The code differentiates total.sum(). Because each object's energy depends only on its own corners, the gradient of the batch sum equals the per-object gradients stacked, shape [B, P, 3].
  • The rows of prescribed corners are set to zero after differentiation. Fusion assigns those corners their exact positions, so their energy derivative is a reaction force that no network output can act on. The adjoint in the next step reads only free rows anyway; zeroing the prescribed rows keeps reactions out of the force residual norm reported later.
  • The returned tensor is detached and shares the dtype and device of positions (float32 on the module device in production).

The mixed-material step supplies energy_total as a closure over this batch's material contexts, so each object is evaluated with its own Lamé parameters, mass and damping coefficient. It supplies project_gradient the same way: each object owns a fusion factor whose weights include that object's Young's modulus, so the adjoint runs per object and the results are concatenated along the batch axis.

Step 2: the fusion adjoint turns corner forces into axis gradients

The network does not move corners. It proposes a dimensionless 3 × 3 axis increment D per cell, and fusion solves for the corner displacement whose sampled deformation change best fits all those increments at once (chapter 03). For a fixed base shape and fixed prescribed positions, the free-corner positions are an affine function of the increments:

x_free(D) = base_free + K_ff⁻¹ (B_f D − K_fp δ_p)

d x_free / d D = K_ff⁻¹ B_f

d E / d D = (K_ff⁻¹ B_f)ᵀ g_free = B_fᵀ K_ff⁻ᵀ g_free

Reading the last line right to left: solve once with the transposed stiffness matrix against the free-corner position gradient, then apply the transposed target operator. This is the chain rule through fusion, and it is exactly what the custom autograd backward of fuse computes during training. project_gradient exposes the same computation as a detached forward operator. The unit test test_fusion.TestHexFusionProjectGradient checks the identity <project_gradient(g), D> = <g_free, fuse(base, D, fixed) − fuse(base, 0, fixed)> and equality with autograd.grad of fuse in float64.

Three properties of this derivative matter for how the feature should be read:

  • It is the derivative with respect to the unscaled world axis increment D. During a query the increment is D = R (A_target − A) = R (s ⊙ correction), where s is the per-cell sigmoid step and correction the bounded nine-value head output. The feature differentiates with respect to D itself, the world increment fusion actually receives; it does not chain back through the frame rotation R or the step multiplier s to the head output correction. It therefore answers the physical question "how much does the energy change per unit change of this cell's world axes, once every shared corner has been reconciled", independently of how the current network parametrizes its output. Step 3 turns it into the derivative with respect to the local increment L = Rᵀ D = s ⊙ correction; neither step involves the sigmoid step multiplier s.
  • No extra stiffness or volume factor is applied. The stiffness matrix K = Gᵀ W G and the target operator B = Gᵀ W T already contain the cell weights E × h³ (joules) and the normalized quadrature weights; see their construction and the weight formula. The adjoint of the map actually used in the forward pass is B_fᵀ K_ff⁻ᵀ and nothing else; multiplying by another factor would make it stop being the derivative.
  • Units come out in joules. g_free is in N = J/m, K_ff in J/m², so z = K_ff⁻ᵀ g_free is in meters and B_fᵀ z, with B in J/m, is in joules. A joule per unit of dimensionless axis change is the natural unit for the derivative of an energy with respect to F.

The implementation packs every object and world component handed to one factor as right-hand-side columns so one sparse solve serves all of them; in the mixed step each call carries a single object, so the packed array is [F, 3]. _columns turns [B, F, 3] into a Fortran-ordered [F, 3B] array; the cached PARDISO factor solves with transpose=True; _target_operator.T (shape [3C, F]) maps the solution to packed target rows; _batch and the final reshape(B, C, 3, 3).swapaxes(-1, -2) restore a world matrix per cell with material axes in columns, the same layout as world_axis_increments in fuse. K_ff is symmetric, so the transposed solve equals the ordinary solve in exact arithmetic; the code uses the transpose path so that this feature and the autograd backward share one code path. Only free-corner rows are read; the trip through NumPy discards any autograd history, so the result is detached by construction.

Step 3: express the gradient in the cell's frame

The world matrix G_world has world components along its rows and material axes along its columns. The network works in each cell's proper rotation frame R, so the gradient is rotated with Rᵀ on the left. This is again the chain rule: with the local increment L defined by D = R L, the derivative with respect to L is Rᵀ dE/dD. The rotation acts only on the row index; the column index, which says which material axis the entry belongs to, is untouched. Because R is orthonormal, the Frobenius norm of each cell matrix is unchanged, so the RMS in the next step does not depend on the frame choice.

The same one-line function serves every matrix block of the state vector: the inertial axis offset Rᵀ (F_Y − F), the physical axis change Rᵀ (F − F_start), the current and previous gradients, and the previous achieved update. The frames come from closest_proper_rotations, computed under torch.no_grad() and returned detached, so multiplying by Rᵀ never adds a differentiable path through the frame.

Step 4: RMS normalization, floor, clip, and the log scalar

Gradient magnitudes vary by orders of magnitude between a soft, nearly settled object and a stiff object far from equilibrium. The network receives the shape of the gradient field and its magnitude separately. One RMS is computed per object over all cells and all nine matrix entries, so the relative size of the gradient between cells of the same object is preserved. The RMS is floored at 1e-12 so a measured zero stays finite (zero in, zero out, and the log of the floor as the scalar). Components are then divided by the RMS and clipped to ±10; the clip is applied to the local-frame entries.

rms_b  = sqrt( mean over c, i, j of G_local[b, c, i, j]² )      shape [B, 1, 1, 1]
rms_b  = max(rms_b, 1e-12)
block  = clip(G_local / rms_b, −10, +10)                         shape [B, C, 3, 3]
scalar = log(rms_b)                                               one value per object, broadcast to every cell

Three fields go through this function with different statistics:

  • The current gradient defines rms_b and is divided by it. Its natural log becomes the log_gradient_rms scalar, one value per object copied to every cell.
  • The previous gradient (from history, first rotated into the current frame) is divided by the current RMS, passed in through the rms argument. The two gradient blocks are therefore in the same units, and their difference is meaningful to the network as a change of the gradient between consecutive queries.
  • The previous achieved update is a dimensionless change of the center deformation, a different quantity in different units, so it is normalized by its own RMS. Its scale is not given to the network as a separate scalar.

The constants live in RMS_FLOOR and CLIP. The function never detaches; the inputs are already detached, so the outputs are constants for backpropagation.

Without history, both history blocks are zero tensors and the flag is false for the whole batch. With history, the blocks are rotated with the current frames and normalized as described, and the per-object flag is copied through.

pack_state_features flattens each 3 × 3 block row-major into nine values and concatenates the five blocks (45 values), the 14 boundary flags, the log RMS (1) and the history flag (1, exactly 1.0 or 0.0), giving the 61-value state vector of STATE_FEATURE_DIM. The network prepends the nine current axes, so each cell token starts from 70 numbers (node encoder input). For objects whose flag is false the two history blocks are overwritten with zeros regardless of the tensors supplied, so a missing history is always distinguishable from a measured zero.

Step 5: the optimizer history

A first-order optimizer that sees only the current gradient cannot estimate curvature or momentum. The step therefore also receives what happened at the previous learned query on the same trajectory: the gradient it saw and the change it actually achieved. Both are stored as world 3 × 3 matrices per cell, not local ones. Frames are recomputed for every candidate and can jump at the tie-break threshold, so storing local matrices would tie the history to a frame that no longer exists; storing world matrices and applying the current Rᵀ at consumption time keeps the two blocks consistent with the rest of the input.

What is stored, and when:

  • Stored gradient: the un-normalized world axis gradient G_world of the query, in joules, exactly the tensor that served as the current-gradient input (before Rᵀ, before RMS division and clipping). Normalizing it later with the next query's RMS is what makes the two gradient blocks comparable.
  • Stored update: the achieved change of the center deformation, F_center(fused) − F_center(candidate), dimensionless. It is derived from the fused positions the query actually produced, not from the network's requested target, so it already includes the reconciliation of shared corners performed by fusion.
  • Written by store_history after every learned query, in the trainer and in both validators, so held-out queries receive the same history the network was trained with.
  • Cleared only when a trajectory is reset: reset writes empty_history, zero blocks and history_valid = False.
  • Carried unchanged across a physical timestep boundary by carry_history: the candidate initializer that follows a timestep never writes history, so the history a new timestep's first query sees is the last learned query of the previous timestep.

The payload keys are history_axis_gradient_world, history_axis_update_world and history_valid. They live inside the trajectory payload dictionaries, so the pool checkpoint carries them and a resumed run continues with the same history. The trainer's factory shows both boundaries: reset attaches an empty history after preparing the physical step, and advance copies the previous payload's history into the newly prepared one.

When a batch is collated, batch_history stacks the per-payload blocks into one OptimizerHistory on the compute device: [B, C, 3, 3] float32 for each block and a [B] boolean flag. Payloads with history_valid false contribute zero blocks. check_history then validates shapes, dtype, device and finiteness inside the step and detaches the blocks once more before assemble_inputs consumes them.

Step 6: the diagnostic outputs and how the trainer uses them

MixedHexSolverStep.forward returns a LearnedHexStepOutput whose trailing fields carry four detached diagnostics next to the fused positions and energies:

  • axis_gradient_world: the un-normalized world gradient G_world, shape [B, C, 3, 3], joules. This is what store_history saves as the next query's previous gradient.
  • achieved_axis_update_world: F_center(fused) − F_center(candidate), computed under torch.no_grad() from detached positions, shape [B, C, 3, 3], dimensionless. This is saved as the next query's previous update.
  • force_residual_norm: the Euclidean norm of the position gradient over all corners and components, shape [B], newtons. Because the prescribed rows are zero, this is the free-corner residual of the objective at the pre-update candidate. The trainer logs it as mean_force_residual_n; validation uses the same quantity per iteration and its final-iteration mean as the checkpoint selection metric (validation residuals).
  • tie_mask: the boolean [B, C] mask from chapter 03, true where the closest-rotation problem for the cell frame was a tie within tie_tolerance, passed through unchanged. The mixed step always decomposes F, so the mask is never None here although the trainer guards for it; the trainer sums it per update and logs tie_cell_count (train_mixed.py:725-727).

In train_mixed.run_training the sequence for one update is: collate the batch with its stacked history, evaluate the pre-update energy without gradients for the loss scale, run the step with history=batch.get("history"), form the loss from the fused energy, backpropagate, take the Adam step, and only then write the history and replace each trajectory's candidate with the detached fused positions. The history written here is consumed by the same trajectory's next query, whether that query is the next inner iteration or the first iteration of the next physical timestep.

Step 7: the one-query detach rule

The gradient feature is a constant for backpropagation. Every stage that produces it breaks the autograd connection: objective_gradient differentiates a detached copy of the candidate and returns a detached tensor; project_gradient passes through NumPy and PARDISO; the frames are computed under no_grad; the history is detached on storage and again when check_history validates it. The state vector the network reads is therefore a plain input, exactly like the boundary flags. The candidate positions themselves are detached leaves in the training batch, so the axes A = Rᵀ F do not carry a gradient to earlier queries either.

What does train is the path from the network output to the fused energy:

network parameters θ
  → correction, step s            (heads)
  → A_target = A + s ⊙ correction
  → D = R (A_target − A)           (frame R is a constant)
  → x_fused = fuse(candidate, D, prescribed)     (custom backward: transposed sparse solve)
  → E_total(x_fused, Y, X_start)  (autograd through elasticity, inertia, damping)
  → local_objective → loss.backward() → Adam

The same transposed solve appears twice in one query: once in the forward pass, as the detached feature that tells the network where the energy decreases, and once in the backward pass, as the true derivative of the fused energy with respect to the network's proposal. Nothing differentiates the network through its own input feature, so there is no second-order term and no unrolling across queries: one query is one forward and one backward. Learning across inner iterations and physical timesteps happens because later queries are trained on states that earlier queries produced, with the detached history telling the network what the previous query saw and achieved.

Two energies at the same candidate, three energy evaluations per update. The trainer evaluates E(candidate) once under no_grad for the loss scale; objective_gradient evaluates it again with gradient tracking to obtain g; the loss evaluates E(x_fused) a third time, differentiably. The first two are constants for the weight update; only the third participates in loss.backward().

Worked shapes for the configured grid

With the 10 × 10 × 40 grid there are P = 4,961 shared corners (11 × 11 × 41), C = 4,000 cells, K = 121 prescribed corners on the minimum-z face and F = P − K = 4,840 free corners. B = 16 objects per GPU.
